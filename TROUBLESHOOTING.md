# TROUBLESHOOTING

Таблица «симптом → причина → чем проверить → как починить».

Пополняется по мере появления настоящих ошибок. Если столкнулся с чем-то, чего
здесь нет, — допиши строку, пока помнишь.

Во всех командах предполагается, что заданы `FACTORY_DATA_DIR` и
`FACTORY_PROJECTS_DIR` — см. [RUNBOOK.md](RUNBOOK.md).

---

## Запуск

| Симптом | Вероятная причина | Чем проверить | Как починить |
|---------|-------------------|---------------|--------------|
| `Каталог данных /data недоступен для записи` | значение по умолчанию рассчитано на контейнер | `echo $FACTORY_DATA_DIR` | `export FACTORY_DATA_DIR=~/factory-data` и добавить строку в `~/.zshrc` |
| `Конфиг проекта 'X' не найден` | не задан каталог с проектами или опечатка в имени | `ls projects/` | `export FACTORY_PROJECTS_DIR=$(pwd)/projects` |
| `factory: command not found` | `uv` не в `PATH` | `which uv` | `export PATH="$HOME/.local/bin:$PATH"` |
| `Проект 'X' не подключён к базе` | конфиг есть, но проект не зарегистрирован | `uv run factory project list` | `uv run factory project add X` |

## Конфигурация

| Симптом | Вероятная причина | Чем проверить | Как починить |
|---------|-------------------|---------------|--------------|
| `Конфиг проекта не прошёл проверку` + список полей | опечатка или пропущенное поле | текст ошибки называет файл и каждое поле | исправить перечисленное; образец — `projects/demo/config.yaml` |
| `неизвестное поле — скорее всего опечатка в названии` | лишняя или переименованная настройка | там же | сверить название с образцом |
| `Файл не читается как YAML` | сбитые отступы или пропущенное двоеточие | текст ошибки указывает строку | выравнять отступы (только пробелы, не табы) |
| `Имя проекта не совпадает с каталогом` | скопировали каталог, но не поменяли `slug` | `head -20 projects/X/config.yaml` | поставить `slug: X`, где X — имя каталога |
| `queue_buffer меньше posts_per_day` | система физически не выпустит столько постов | раздел `limits` | поставить `queue_buffer` ≈ `posts_per_day × 3` |
| `Не найден секрет для ...` | ключа нет в файле секретов | `grep ИМЯ_ПЕРЕМЕННОЙ ~/factory-data/.env` | добавить строку `ИМЯ=значение`, затем `chmod 600` |

## Работа воркера

| Симптом | Вероятная причина | Чем проверить | Как починить |
|---------|-------------------|---------------|--------------|
| Посты стоят, в логах пусто | воркер не запущен | `uv run factory doctor` → строка про последний тик | запустить `uv run factory run --loop` |
| `Тик пропущен: уже работает другой процесс` дольше получаса | блокировка осталась от убитого процесса | `uv run factory doctor` | `uv run factory unlock` |
| Посты доходят до `approved` и стоят | исчерпан дневной лимит или сейчас не время публикации | `uv run factory post show N` | это нормально; проверить `limits.posts_per_day` и `vk.schedule` |
| Пост в состоянии `failed` | пять неудачных попыток подряд | `uv run factory post show N` — там текст ошибки | устранить причину, затем `uv run factory post retry N` |
| Пост в `in_review` не двигается | ждёт кнопки в Telegram | `uv run factory post show N` | нажать кнопку; до Этапа 5 поставить `review.mode: auto` |
| `свободные темы закончились` | очередь тем пуста | `uv run factory topics list X` | `uv run factory topics import X файл.txt` |
| В логах WARNING про `FACTORY_IGNORE_SCHEDULE` | включён режим разработки | `echo $FACTORY_IGNORE_SCHEDULE` | `unset FACTORY_IGNORE_SCHEDULE` — иначе посты уйдут ночью |

## База данных

| Симптом | Вероятная причина | Чем проверить | Как починить |
|---------|-------------------|---------------|--------------|
| `database is locked` | два процесса пишут одновременно | `ps aux \| grep "factory run"` | оставить один воркер; лишние остановить |
| `Миграция NNN не применилась` | повреждён или изменён файл миграции | текст ошибки называет файл | база осталась на прежней версии и работает; восстановить файл из репозитория |
| `Миграция нарушила связи между таблицами` | миграция забыла перенести строки | текст ошибки называет таблицы | изменения отменены; исправить миграцию, см. `CLAUDE.md` → «Как менять схему базы» |
| Подозрение на порчу файла базы | внезапное отключение питания | `sqlite3 ~/factory-data/factory.db "PRAGMA integrity_check"` | если не `ok` — восстановить из бэкапа |

## Картинки и файлы

| Симптом | Вероятная причина | Чем проверить | Как починить |
|---------|-------------------|---------------|--------------|
| `ФАЙЛ ПРОПАЛ` в `post show` у неопубликованного поста | почистили временный каталог | `ls $FACTORY_TMP_DIR` | ничего не делать: следующий проход сгенерирует картинку заново |
| `удалена после публикации` | так и задумано | — | это не ошибка: после публикации файлы убираются, чтобы не копиться |
| Место на диске кончается | остались файлы недоведённых постов | `du -sh $FACTORY_TMP_DIR` | удалить каталоги постов, которые уже в `failed` или `rejected` |

## Публикация

*(актуально с Этапа 2)*

| Симптом | Вероятная причина | Чем проверить | Как починить |
|---------|-------------------|---------------|--------------|
| Один и тот же пост вышел дважды | процесс убили между отправкой и записью результата | сравнить `external_id` в базе с тем, что в группе | удалить лишний пост в группе руками; см. примечание ниже |

**Про дубли.** Система защищена от повторной публикации проверкой в базе, но есть
узкое окно: если процесс убить ровно между отправкой в ВК и записью результата,
следующий проход опубликует пост ещё раз. Окно закроется на Этапе 2, когда
появится настоящий публикатор с идентификатором операции (`guid` в ВК API).
До тех пор не убивай воркер командой `kill -9` во время окна публикации.

## Как собрать сведения для разбора

Если ничего из перечисленного не подошло, собери это перед тем, как просить
помощи:

```bash
uv run factory doctor
uv run factory post list
tail -n 100 ~/factory-data/worker.log
sqlite3 ~/factory-data/factory.db "PRAGMA user_version; PRAGMA integrity_check;"
```

В логах не бывает токенов и ключей — они вычищаются автоматически, поэтому вывод
можно показывать целиком.
