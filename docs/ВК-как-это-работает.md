# ВК: как устроена публикация

Всё, что выяснено опытом на живом API в августе 2026. Документация ВК описывает
последовательность вызовов, но умалчивает про главное — какой ключ что может.
Здесь записано и то, и другое, чтобы не выяснять заново.

Официальная инструкция по загрузке:
<https://dev.vk.com/ru/api/upload/wall-photo>

---

## Главное: нужны ДВА ключа, не один

Ни один ключ не проходит цепочку целиком. Это не наша выдумка и не обход —
ВК развёл права по типам токенов, и каждый ключ делает то, что ему разрешено.

| Шаг | Каким ключом | Почему не другим |
|-----|--------------|------------------|
| `photos.getWallUploadServer` | **пользователя** | ключу сообщества метод недоступен: ошибка 27 |
| загрузка файла на `upload_url` | **пользователя** | продолжение того же шага |
| `photos.saveWallPhoto` | **пользователя** | то же |
| `wall.post` | **сообщества** | ключу пользователя запрещён: «denied for non-standalone applications» |

Пост выходит от имени сообщества — за это отвечает `from_group=1`, и в ответе
`wall.getById` поле `from_id` отрицательное.

## Что где взять

### Ключ сообщества — `VK_TOKEN_GROUP`

Группа → **Управление** → **Работа с API** → **Ключи доступа** → создать.
Права: **Фотографии, Стена, Управление сообществом**.

Бессрочный. Умеет `wall.post`, не умеет ничего из загрузки файлов.

### Ключ пользователя — `VK_UPLOAD_TOKEN`

Нужно приложение. Создаётся на <https://dev.vk.com/> → «Создать приложение» →
тип **Мини-приложение** (Standalone из формы убрали, см. ниже).

После создания приложение надо **включить**: Настройки → **Размещение** →
«Состояние для пользователей» → **Включено**. Форма потребует URL — подойдёт
`https://example.com`, приложение никто не откроет, оно нужно только ради ID.

Дальше открыть в браузере ссылку авторизации и нажать «Разрешить»:

```
https://oauth.vk.com/authorize?client_id=54733282&display=page&redirect_uri=https%3A%2F%2Foauth.vk.com%2Fblank.html&scope=photos&response_type=token&v=5.199
```

Откроется пустая страница, токен — в адресной строке между `access_token=`
и `&expires_in`.

**Живёт 24 часа.** Это главная нерешённая проблема, см. ниже.

### Где хранятся

`~/factory-data/.env`, права `600`. В репозиторий не попадают никогда.

```
VK_TOKEN_GROUP=vk1.a....     ключ сообщества, бессрочный
VK_UPLOAD_TOKEN=vk1.a....    ключ пользователя, сутки
```

| В `wall.post` | `owner_id = -111222333`, то есть минус id группы |

## Полная последовательность

1. `photos.getWallUploadServer` с `group_id` → получаем `upload_url`.
2. `POST` на `upload_url`, `multipart/form-data`, **поле `photo`**, формат **PNG**.
   Ответ: `server`, `photo`, `hash`.
3. `photos.saveWallPhoto` с этими тремя полями → `owner_id` и `id`.
4. `wall.post` с `owner_id=-111222333`, `from_group=1`, `message`,
   `attachments=photo{owner_id}_{id}`.

Ограничения на картинку: сумма сторон не более 14 000 пикселей, файл не больше
50 МБ, соотношение сторон не менее 1:20. Наши 1080×1350 проходят с запасом.

## Куда девается картинка

Загруженная картинка сохраняется в служебный альбом **личного профиля**
(`owner_id` положительный). Но при публикации от имени сообщества **ВК копирует
её в группу**: в самом посте вложение уже с отрицательным `owner_id`.

Проверено: у постов `-111222333_3` и `_4` картинки принадлежат группе.

В личном профиле остаётся невидимый след в системном альбоме «фото со стены» —
в интерфейсе он не показывается, но через API виден. Со временем копится.
Чистится методом `photos.delete` после успешной публикации; на Этапе 2 стоит
это добавить.

Право `groups` в токене принадлежность **не меняет** — проверено, картинка всё
равно сохраняется на профиль.

## Что проверено и НЕ работает

Чтобы не пробовать заново. Все ошибки получены на живом API.

### Ключ сообщества не может загрузить ни одной картинки

| Метод | Ошибка |
|-------|--------|
| `photos.getWallUploadServer` | 27 — недоступен групповой авторизации |
| `photos.getUploadServer` (в альбом) | 27 |
| `photos.getMarketUploadServer` | 27 |
| `photos.getMessagesUploadServer` | 901 — нужен настоящий собеседник |
| `docs.getWallUploadServer` | 15 |
| `docs.getUploadServer` | 27 |
| `photos.getAlbums`, `photos.createAlbum` | 27 |
| `stories.getPhotoUploadServer` | **работает**, но истории живут сутки и постом не являются |

Ключу сообщества недоступен и `wall.delete` (ошибка 27) — тестовые посты
приходится удалять руками.

### Сервисный ключ приложения не годится

Ошибка 28: «method is unavailable with service token». Бессрочный, но
бесполезный для загрузки.

### VK ID не даёт нужных прав

Приложение, созданное в <https://id.vk.ru/>, в разделе «Доступы» предлагает
только личные данные, почту и телефон. Запрошенные `photos wall` при авторизации
молча отбрасываются — выдаётся `vkid.personal_info`.

Токены VK ID имеют формат `vk2.a.*` и с методами VK API несовместимы в принципе,
это известная проблема: <https://github.com/gitroomhq/postiz-app/issues/1408>

### Standalone-приложение создать нельзя

С 10 апреля 2026 их создание перенесено в VK ID, а там нужных прав не дают.
На dev.vk.com в форме остались только мини-приложение, игра и плагин.
Старые standalone-приложения продолжают работать.

### Право `offline` отменено

Именно оно делало токен бессрочным. Сейчас отвечает «invalid scope» —
проверено и на implicit-схеме, и на серверной.

## Нерешённое: токен загрузки живёт сутки

Проверены все три способа получить токен, результат одинаковый:

| Способ | Срок | `refresh_token` |
|--------|------|-----------------|
| Implicit (`response_type=token`) | 86400 сек | нет |
| Серверная схема (`response_type=code` + защищённый ключ) | 86229 сек | **нет** |
| Сервисный ключ | бессрочный, но грузить не умеет | — |

Пока не решено. Варианты:

1. **Обновлять вручную раз в сутки.** Система напоминает в Telegram, владелец
   открывает ссылку и вставляет новый токен. Минута в день.
2. **Просить поддержку** <devsupport@corp.vk.com> открыть `offline` для
   приложения 54733282. Обоснование: своя закрытая группа, свой контент.
3. **Telegram как основная площадка.** Там таких ограничений нет вовсе.

## Сеть до ВК нестабильна

При разработке с российского IP рукопожатие TLS занимало от 3 до 11 секунд,
часть запросов отваливалась по таймауту совсем. Это не ошибка кода.

Следствия для провайдера:

- ретраи обязательны на всех **идемпотентных** вызовах
  (`photos.getWallUploadServer`, `photos.saveWallPhoto`, загрузка файла);
- на `wall.post` ретраев быть не должно — см. «Задолженность Этапа 2» в
  `CLAUDE.md`: ответ мог не доехать, а пост уже создан;
- прокси для ВК настраивается через `VK_PROXY`, см. `core/http.py`.

Отдельно: сервер загрузки иногда возвращает `photo: ""` при формально успешном
ответе. Это не ошибка формата — повторный заход с новым `upload_url` проходит.
Провайдер обязан это учитывать.
